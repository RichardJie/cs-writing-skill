# Plain：用本领域的具体例子把概念讲成人话

解释的目标不是把术语换成更简单的术语，而是找到用户理解中装错或缺失的那个零件，并把它修好。

## 工作流程

### 1. 先定位用户究竟卡在哪里

回答前先判断：

- 用户目前认为流程或机制是怎样的？
- 哪一部分理解是对的？
- 哪一个概念被混淆、遗漏或错误连接？

开头直接给诊断结论，例如：“你前半段理解是对的，真正差在 X”“这里把两个不同的量混在了一起”。
这不是客套；它告诉用户哪些部分可以保留，不必从头重学。

不要用“你完全理解错了”把用户已有的正确框架一起推翻。

### 2. 把绕不开的术语翻成人话

存在多个生词时，先给两列表：

| 术语 | 在当前问题里具体指什么 |
|---|---|
| 某术语 | 不含其他新术语的直接说明 |

要求：

- 不用一个行话解释另一个行话。
- 一行只解释一个概念。
- 如果只是历史惯例，直接说它是惯例，不为它编造原理。
- 若只涉及一两个词，可在正文中顺手解释，不为形式强行制表。

### 3. 只用当前领域真实存在的对象举例

例子必须来自正在解释的问题本身。讲视频 token 就用帧、视觉 token、层和预测答案；讲梯度下降就用参数、
损失和一次更新；讲数据划分就用具体样本。

默认禁止用山、温度计、快递、流水线等跨领域比喻。跨领域类比会让用户先学一个新世界，再映射回来，
容易掩盖真正的机制。只有用户主动要求类比时才可简短使用，并马上映射回原对象。

### 4. 用一组小数字逐步走完整流程

选择一组规模很小、可以逐行验算的数据，并在整轮答疑中复用它。

必须做到：

- 每一步单独写明输入、操作、输出。
- 数字要小而具体，不用 `x`、`σ`、`Σ` 代替关键内容。
- 对比结论用同一份输入并排计算。
- 结论必须能直接从例子里的数字看出来。
- 不用省略号、“重复 N 次”“其余同理”跳过决定结论的中间步骤。
- 实验数字若经过扣除基线、归一化或差上加差，先分别算出原始量和校正项，再算论文报告的量；
  不得把校正后的统计量说成原始准确率变化。

若完整过程太长，缩小例子规模，而不是省略步骤。

数字例子用于解释机制时，必须明确写“下面是为了讲清机制而设的小例子”，不得让示例数字看起来像真实实验结果。

### 5. 沿用用户已经建立的框架

如果用户已经用自己的例子、编号或流程复述：

- 先指出其中正确的部分。
- 沿用用户的对象、编号和顺序。
- 只补上缺失的零件，再按原框架走一遍。
- 不要偷偷换成另一套更方便回答者、却让用户重新映射的例子。

如果先前用了类比而用户质疑，撤回类比，直接改用领域数据说明。

### 6. 拆开容易混淆的两个概念

优先检查这些常见混淆：

- 训练集、验证集、测试集
- 模型输入、模型中间状态、最终读出位置
- token 所在的位置、token 向量已经携带的信息
- 相关、干预证据、因果结论
- 原始指标、由指标推导出的差值
- 模型学到的规律、评测代码做的后处理
- 说明某个模块有效、说明该模块不可替代

分别给定义和同一数字例子，不要把两者混在一个长段落里。

解释具体模型结构时，先检查实际实现中的 hook 位置、token 排列和注意力掩码。不能只凭模型名称或常见架构
猜测某个位置已经看到了哪些 token。

### 7. 回到用户真正关心的主线

末尾用一两句话回答：

- 这件事现在能说明什么？
- 不能进一步推出什么？
- 如果用户在做研究或决策，下一步最有区分度的检查是什么？

不要用一长串免责声明冲淡主结论。证据边界只写到避免误解所需的程度。

## 推荐回答结构

1. 一句诊断：用户哪里对、差在哪里。
2. 必要时给名词翻译表。
3. 用一个贯穿的小数字例子逐步走流程。
4. 直接回答用户列出的每个问题。
5. 一句话把修正后的理解接回主线。

## 反模式

| 反模式 | 症状 | 修正 |
|---|---|---|
| 术语套娃 | 用另一个生词解释当前生词 | 直接说它在这个流程里输入什么、输出什么 |
| 跨领域类比 | 用山、快递或温度计解释模型机制 | 换成该模型中的真实 token、层和数字 |
| 抽象正确 | 全文没有一个具体数字 | 加一组可逐行验算的小例子 |
| 跳步 | 用省略号或“其余同理”略过关键过程 | 缩小例子并把每一步写全 |
| 全盘否定 | 直接说用户理解错了 | 保留正确部分，只替换错误连接 |
| 框架霸权 | 用户已有例子，回答者又换一套 | 在用户的框架里修正 |
| 假深意 | 为惯例或偶然数字编造机制 | 明说它是约定、实现选择或尚无证据 |
| 示例冒充结果 | 为解释随手设的数字没有标注 | 明确说明是讲解示例，不是真实结果 |
| 免责声明淹没答案 | 先写很多“不能说明” | 先讲能说明的主结论，再补必要边界 |

## 质量检查

回答前检查：

- 用户能否只看这组例子就复算结论？
- 是否出现了未解释的新术语？
- 是否把“视觉 token 的位置”误说成“只含视觉外观、不含时间信息”一类概念混淆？
- 是否把扣除基线后的受控差值误说成原始准确率下降？
- 涉及具体模型时，hook、token 顺序和注意力可见范围是否来自实际实现？
- 是否把示例数字和真实结果明确区分？
- 是否直接回答了用户问的“所以呢”？
